* Glossary: ETM vs SWO

These two are at /different layers/ of the same trace pipeline, not alternatives: one /generates/ trace data, the other /carries/ it.

#+begin_example
DWT  (PC-match comparator)  ┐
ETM  (instruction trace)    ├─→  TPIU  ─→  SWO            (1 wire)   → TraceWhisperer
ITM  (software trace)       ┘  (formatter)  or TRACEDATA[3:0] (4 wires, "parallel")
#+end_example

- *DWT* — source/trigger: comparators that fire on a PC-address match (=COMP0= = =fpr_scaled= entry).
- *ETM* — source/generator: emits the I-sync packet (carrying the PC address) when triggered.
- *TPIU* — formatter: funnels and frames packets from the sources.
- *SWO* — transport: the single-wire output mode of the TPIU; the physical link to the Husky. The alternative is 4-wire parallel =TRACEDATA[3:0]=.

Rule of thumb: say *ETM* for /what is captured/ (the PC-address events), and *SWO* for /the link and its bandwidth/. The causal chain here: a DWT PC-match makes the ETM emit a packet, which is serialized over the SWO wire; when the loop produces matches faster than SWO can drain them, the ETM/TPIU FIFO overflows. The events are ETM; the bottleneck is SWO. Switching to parallel trace changes only the transport (SWO → =TRACEDATA[3:0]=, ~4× bandwidth); the ETM source and DWT triggers are unchanged.


* Issues of ARM ETM in O1, O2, O3, Os

The =fpr_scaled= body is byte-identical across all levels (it is naked asm), so the function is not the cause. What differs is how fast the surrounding =smallints_to_fpr= loop calls it. The per-call spacing is =smallints_to_fpr / 512= (from the cycle table in ~1_cycle_usage.org~):

| level | cycles / =fpr_scaled= call |
|-------+--------------------------|
| O0    | 68687 / 512 ≈ 134        |
| O1    | 37897 / 512 ≈ 74         |
| O2    | 36872 / 512 ≈ 72         |
| O3    | 36872 / 512 ≈ 72         |
| Os    | 37383 / 512 ≈ 73         |

** Diagnosis: SWO trace bandwidth saturation

The trace path is single-wire SWO. In =enable_trace()= the baud is set by =TPIU->ACPR = 0=, i.e. *1 SWO bit per CPU cycle* (already the maximum, no headroom). One ETM I-sync packet (header + address + info, plus TPIU framing from =FFCR = 0x102=) is roughly *6-8 bytes ≈ 50-85 cycles* to serialize. So each =fpr_scaled= match needs the calls to be spaced more than ~85 cycles apart for the SWO link to keep up:

- *O0 (≈134 cycles/call):* the unoptimized loop spaces the calls well above the packet time → SWO drains between events → all 512 events are captured.
- *O1 / O2 / O3 / Os (≈72-74 cycles/call):* the optimized loop fires events at or below the packet-serialization limit → the ETM FIFO backs up and overflows within a few iterations.

Periodic SYNC is *disabled* (=DWT_CTRL = 0x40000021=, ITM =SYNCENA = 0=), so after the first overflow there is *no resync packet to recover alignment* — the bytestream stays desynced for the rest of the run. The signature is: the first event is captured, then everything after is lost.

Things that do /not/ help (all frequency- and PPC-independent, because the problem is the SWO-vs-code /ratio/): changing =PPC= (the SWO clock is =clkgen_freq × 8=, independent of =adc_mul=), changing =MCU_FREQ= (code speed and SWO baud scale together), or changing the match end address.


** Fixes

- *Use the O0 build* (chosen here): its wide per-call spacing keeps SWO drained, so all 512 events come through.
- *Parallel trace:* the Husky supports 4-bit TPIU parallel trace and the firmware already sets =TPIU->CSPSR = 0x8= (4 lanes); switching =tracewhisperer_husky_setup= from ='SWO'= to ='parallel'= gives ~4× bandwidth, enough for the optimized levels. Requires the =TRACEDATA[3:0]= pins wired on the 20-pin trace header.
- *Cycle usage only:* if only =expected_delta= / total cycles are needed (not the per-call address dict), skip ETM and bracket =smallints_to_fpr= with =HAL_CYCCNT=, as in ~1_cycle_usage.org~.

Explanation to the exampled print out:

In =fft.c=, =Zf(FFT)= (= =falcon_inner_FFT=)

#+begin_src C
void
Zf(FFT)(fpr *f, unsigned logn) {
    n = (size_t)1 << logn;
    hn = n >> 1;  /* half n */
    t = hn;
    for (u = 1, m = 2; u < logn; u ++, m <<= 1) { /* ← logn */
        ht = t >> 1;  /* half t */
        hm = m >> 1;  /* half m */
        for (i1 = 0, j1 = 0; i1 < hm; i1 ++, j1 += t) {
            for (j = j1; j < j2; j ++) {
                x_re = f[j];
                x_im = f[j + hn];
                y_re = f[j + ht];
                y_im = f[j + ht + hn];
                FPC_MUL(y_re, y_im, y_re, y_im, s_re, s_im);  /* 4 consecutive fpr_mul called */
            }  /* ) */
        }
    }
}
#+end_src

calls macro function =FPC_MUL=:

#+begin_src C
/*
 * Multplication of two complex numbers (d = a * b).
 */
#define FPC_MUL(d_re, d_im, a_re, a_im, b_re, b_im)   do { \
        fpr fpct_a_re, fpct_a_im; \
        fpr fpct_b_re, fpct_b_im; \
        fpr fpct_d_re, fpct_d_im; \
        fpct_a_re = (a_re); \
        fpct_a_im = (a_im); \
        fpct_b_re = (b_re); \
        fpct_b_im = (b_im); \
        fpct_d_re = fpr_sub( \
                             fpr_mul(fpct_a_re, fpct_b_re), \    /* ← HERE */
                             fpr_mul(fpct_a_im, fpct_b_im)); \   /* ← HERE */
        fpct_d_im = fpr_add( \
                             fpr_mul(fpct_a_re, fpct_b_im), \    /* ← HERE */
                             fpr_mul(fpct_a_im, fpct_b_re)); \   /* ← HERE */
        (d_re) = fpct_d_re; \
        (d_im) = fpct_d_im; \
    } while (0)
#+end_src
