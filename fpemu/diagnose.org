=DWT_FUNCTION0=8= (CMPMATCH → ETM trigger only, no DWT data packet), the SWO line
stays completely idle.

The bug is in =enable_trace()=: it writes =ETM->CR = 0x1= (ETMEN=1) which exits
programming mode, but the subsequent =ETM_TraceMode()= call inside =set_isync_matches=
reads back the hardware *reset* value =0x800= (bit[11] is hardwired=1 in this ETM
implementation) and writes =0x800 & ~0x20 = 0x800= -- silently clearing ETMEN.

=ETM_TraceMode()= reads =0x821=, clears only bit5, and writes =0x801= (ETMEN=1).

*Root cause analysis*: The "fix" above was wrong.  =arm_etm.h= defines:
- =ETM_CR_POWERDOWN = 0x00000001= (bit 0) — NOT ETMEN
- =ETM_CR_PROGRAMMING = 0x00000400= (bit 10) — NOT bit 5
- =ETM_CR_ETMEN = 0x00000800= (bit 11) — NOT bit 0

So =ETM->CR = 0x800= was already *correct* (ETMEN=1, PROGRAMMING=0, POWERDOWN=0).
Writing =0x821= set POWERDOWN=1 (bit0) and PORTSIZE_16BIT=1 (bit5) — corrupting ETM state.

Separately, =enable_trace()= writes =TPIU->CSPSR = 0x8= (4-bit parallel port) even
though =SPPR=2= selects SWO (1-bit serial).  CSPSR must be =0x1= for SWO output.

Fix:
1. Restore =ETM->CR = 0x800= (setreg 3, val 0x00000800)
2. Set =TPIU->CSPSR = 0x1= (setreg 11=0x0b, val 0x00000001)
